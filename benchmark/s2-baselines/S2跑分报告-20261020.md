口径注记：
- **可检出子集**：E11/E14/E15/E16 四类的 ground truth 差异在金额层（无行引用），行级定位理论上限 71.8%（3700/5150）；该列=归一化后的公平口径。
- **行 precision 近零的原因**：前两个基线是撒网式（每实例平均 50-80 条预测，规则引擎 404,800/5600≈72 条/实例），跨 profile 范式错配+行内弱信号全部报出。**这是论文论据不是缺陷**：现有方法报得出一堆"可疑行"但定位不出真正的错误行；类级+行级精确定位是 LLM 对账员的对照位。
- 规则引擎用 intercom 语义跑全部 7 profile（跨范式错配的实证）；zendesk 语义在 counts-only CSV 上全 CANNOT_SETTLE（llm_verified_only trigger，本跑分未采用）。
- direction_acc=预测行命中 GT 行时方向（over/under）一致的比例；semantic_mislabel 类（662 条）无金额方向，计入分母压低该值。

## LLM 对账员（被测系统 d，两步式）

- **Step 1 已交付**：`llm-prompts-sample.jsonl`（200 条子样本，含完整规则文档+发票 JSON+16 类输出 schema 的 prompt，2.9MB）。
- **Step 2（包外调模型）**：接 `eval_reconciler.call_llm()` 或任意 chat/completions 端点跑 prompts → 按 OUTPUT_SCHEMA 解析 → `eval_reconciler.py --reconciler llm` 评分（类召回/精确匹配/行引用命中/置信度）。协议=框架 §11.1（temperature=0、3 次方差、模型组 GPT/Claude/Gemini+开源锚点、token 成本记录）。
- 纪律：amsbench 包内禁 subprocess/禁真实模型调用；模型调用与成本记录在包外完成（两步式）。

## 方法学边界（写论文时须引用）

1. 规则引擎基线 import 仓库 `am_healthcheck.vendors.recount`（被测系统本体），驱动器在 amsbench 评测包外——双实现隔离声明不受影响（生成器/校验器/评分器与被测引擎仍零共享）。
2. 事件流重建用生成器 `synth_events`（seed 可复现）=对账员取得厂商 conversation log 的模拟；重建结果与 validate.py V4 同源。
3. 基线实现各自的判定映射在 `s2_baselines.py` 头部注释（D1-D4 / z-score 规则），无 ground truth 泄漏（三个基线均不读 `ground_truth` 字段）。

## 复现

```bash
cd 代码仓库/benchmark/s2-baselines
python3 s2_baselines.py                    # 全量三基线（~13s）
python3 s2_baselines.py --llm-prompts 200  # 生成 LLM step1 prompts
# LLM step2（包外）：用任意模型端点跑 llm-prompts-sample.jsonl 的 prompt 字段，
# 输出 {"discrepancies":[...]} 后接 amsbench/eval_reconciler.py 评分。
```
